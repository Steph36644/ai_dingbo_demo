图 4　落地顺序（刚性）

顺序不能交换。跳过 token 直接改样式，等于把技术债从「10 处硬编码」变成「30 处硬编码 + 两套并存」。

R1 · 第一步

Token 表

建立全站唯一颜色与规格来源，替换全部硬编码色值。此步不改任何布局。完成判据：grep 全站再无十六进制色值。

R1 · 第二步

骨架

顶栏 / 三 dock 容器 / 底部状态栏 / toast / 模态。此时面板内容还是旧的，但外壳已经是新的。

R2–R3

面板迁移

各 dock 内容逐个迁入新外壳，只换 class，不碰行为。行为修复留到 R4，避免样式与逻辑同时变动导致问题定位困难。

R4

缺口闭合

G2 断屏提示接线、G5 pin / dismiss 语义修正、G6 显示器持久化、G8 全屏去边框等行为修复。G4 Stage 通道只读已随 PR #22 合入 main，本版不重做，只随 R6 做验收复验。

反例

跳过 token

直接改 `.css` 表面上更快，实际会产生新旧两套色值并存。下一次改视觉要再翻一遍全站，且两端必然不一致 —— 这正是现状问题的成因。

视觉验收自检四问：
① 层级靠描边 / 标题栏，还是靠亮色块？　② 同一状态在这屏出现了几次？
③ 这条提示需要「处理」还是只需「知道」？　④ 新写的 CSS 里有十六进制色值吗？
