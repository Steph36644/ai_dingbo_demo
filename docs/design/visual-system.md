# 视觉系统设计思路（v1.0.0 规划稿）

> 本文是 **设计思路与执行依据**，回答「为什么这么设计、怎么落地」。
> 具体规格数值（token 表、尺寸、间距、字号）以 [PRD v1.0.0 §4](../prd/latest.md) 为准，本文不重复抄写，避免两处漂移。
> 状态：规划稿，未进入实现。对应 PRD v1.0.0 §4 / §9（R1–R6）。

---

## 1. 一句话

**借 OBS 的外壳逻辑，不借它的功能。**

把「直播中专业控制台」的空间结构、信息密度、注意力分配方式，搬到盯播域。功能隐喻一律不照搬。

---

## 2. 为什么对标 OBS

只回答一个问题：**为什么是 OBS，而不是仪表盘、剪辑软件或普通后台？**

因为使用场景同构，四项都对得上：

| 场景特征 | OBS | AI盯播 |
|----------|-----|--------|
| 长时间挂机运行 | 数小时连续直播 | 一场直播 1–4 小时 |
| 弱光环境注视 | 直播间常关灯 | 同理 |
| 一屏内完成闭环 | 配置 → 监看 → 响应，不换页 | 来源 → 监视 → 处置，不换页 |
| 同时服务两类观众 | 操作者看主窗，观众看输出 | 助播看 Control，主播看 Stage |

最后一条是关键：**OBS 是少有的、把「操作者界面」和「观众输出界面」在同一产品里彻底分开的桌面软件**。Control / Stage 双端不是我们发明的，它和 OBS 主窗 + 投影窗是同一个结构问题。

---

## 3. 借什么，不借什么

这条边界必须先划清，否则会做出「假功能」。

| 借（结构） | 不借（功能） | 不借的理由 |
|-----------|-------------|-----------|
| dock 工作区（可折叠面板） | 推流 / 录制按钮（**出站动作**） | 盯播不做推流出站。**提醒控件另算**：PRD A5 已裁定本版要画推流 / 发券提醒，但它是「该推了」的提示，不是把画面播出去 |
| 来源列表 + 属性面板 | Multiview 多画面宫格 | 只有一路音源，宫格无意义 |
| 场景列表 → 阶段列表 | 音轨推子与分贝刻度 | 不做假精度，环回只需「有没有声音」 |
| 输出投影窗（无 UI） | 转场动画 | 阶段切换是语义切换，不是视觉表演 |
| 底部常驻状态条 | 插件体系 | 单机工具，无扩展需求 |
| 深色 / 高密度 / 小圆角 / 细描边 | 主题市场 | 弱光专业工具，主题是干扰项 |

一句话记法：**凡是 OBS 里为了「把画面播出去」而存在的控件，一律不借；凡是它为了「让人长时间稳定操作」而存在的结构，一律借。**

## 4. 三条硬规矩

这三条是本次重构真正的判断标准。满足它们，视觉问题就解决了大半。

### 规矩一：层级靠结构，不靠明度反差

**现状问题**：深色底上漂浮浅色纸卡（`#F6F1E6` 一类），用「越亮越重要」表达层级。结果是浅色岛互相抢焦点，层级完全混乱，且和弱光环境直接冲突。

**改法**：三件工具替代明度反差 ——

1. **描边**（`--border-0` 细线）划定区域边界
2. **面板底色**（`--bg-1`）区分容器与窗口底
3. **标题栏**（13px 小标题 + 可选操作按钮）声明这块区域是什么

层级由「哪块有标题栏、哪块被描边包围、哪块在容器里」决定，不由亮度决定。

### 规矩二：状态收敛到两处

**现状问题**：同一件事（比如「是否有未读」「是否健康」）在 pill、footer、健康灯三处各说一遍，且措辞和颜色不一致。

**改法**：

- **常驻状态** → 底部状态栏（唯一）
- **当前态摘要** → 顶栏 pill（唯一）

其他任何位置不再重复表达同一状态。Stage 的健康点是**例外且唯一例外**，因为它服务的是另一个观众（镜头前的人），不是冗余。

### 规矩三：反馈按「是否常驻」分流

**现状问题**：一次性提示（如落盘失败）也用 banner，挤占布局，且不会自己消失。

**改法**：

| 类型 | 载体 | 判断标准 |
|------|------|----------|
| 常驻阻断 | 内联 banner（留在原区域） | 不解决就不能继续（凭据未配、框架加载失败） |
| 一次性事件 | toast（右下角，5s 自动消失） | 知道就行，不影响继续（断屏、落盘失败、切换成功） |
| 破坏性动作 | 模态确认 | 不可逆（停播、清空笔记、清除凭据） |

## 5. 工程前提：必须先做 token 化

**这是 R1 排在最前面的原因，不是审美问题，是维护性问题。**

现状证据：

- `#f2c14e` 一类色值散落在 10+ 处
- `stage.css` 与 `styles.css` 的绿色**不一致**
- 圆角从 4px 到 22px 无规律分布

含义很直接：**当前没有唯一颜色来源**。改一次视觉要翻遍全站 CSS，且必然漏改，导致两端不一致。

所以顺序是刚性的：

```
token 表落地（唯一来源）
    ↓
骨架替换（顶栏 / 三 dock / 状态栏 / toast / 模态）
    ↓
各面板迁移（此时只换 class，不碰行为）
    ↓
缺口闭合（行为修复）
```

如果跳过 token 直接改样式，等于把技术债从「10 处硬编码」变成「30 处硬编码 + 两套并存」。

## 6. Control 结构：三个有标题栏的 dock

### 6.1 从「一列控件 + 两块分析面板」到「三 dock」

现状是纵向堆叠，功能区无边界，靠间距和色块暗示分组。

改为三个**有明确职责边界**的 dock：

| dock | 职责 | 回答的问题 | OBS 对应 |
|------|------|-----------|----------|
| 左 | 输入：音源、ASR、预检、开始/停止 | 「我听谁的？健康吗？能开始吗？」 | 来源列表 + 属性面板 |
| 中 | 监视与处置：字幕监视器 + 问题 + 覆盖 | 「现在讲到哪？哪里讲偏了？」 | 预览监视器 |
| 右 | 输出与旁路：阶段、抬头屏、品备注、笔记、推流 / 发券提醒 | 「下一段讲什么？该推该发了吗？」 | 场景列表 |

**为什么是这三个而不是别的切法**：它对应操作者的三个时间维度 —— 开播前（左）、进行中（中）、即将发生（右）。左是「准备态」，中是「此刻态」，右是「下一态」。

每个 dock 统一结构：13px 标题栏（可含操作按钮）+ 内容区，标题栏点击折叠，折叠状态记入本机。

### 6.2 底部状态栏为什么必须常驻

长时间盯播中，最怕的不是信息不够，是**关键健康信息滚出视野**。

状态栏固定在窗口底，永远可见，字段：状态 / 采音时长 / 音源 / ASR / 落盘 / 未读 + 固定声明「内容盯播，不是 GMV 总控」。

最后那句声明不是装饰 —— 它防止用户把本工具误当成经营总控，是本产品的**边界宣示**。

### 6.3 工作区切换：平级，不是斜切

「回看」不再是盯播页上的一个临时模式切换，而是与「盯播」「设置」平级的独立工作区。理由：回看时用户的心智是「我在看历史」，不是「我在盯播但暂停了」。骨架复用（左 dock = 场次目录，中央 = 只读监视器），但语义独立。

## 7. Stage 结构：输出窗化

Stage 走完全相反的方向：**不做减法，而是做归零**。

它不是「Control 的精简版」，而是 OBS 投影窗的等价物 —— 一个没有菜单、没有设置、没有可点控件的**纯输出面**。

五要素位置锁死：

1. **阶段大字**（中央上部，56–72px）→ 比原来**向上移**
2. **至多一条建议**（阶段下方，左缘 4px 语义色）→ 也向上移
3. **字幕区**（底部占满，独立底色容器，固定高度，水平居中）→ 历史 1–3 行渐隐，当前句在最底行全亮；超出时容器内上滚，不撑高挤压上方
4. 未读角标（右上）
5. 健康点 + 排练标记（同一行，左上角）

为什么是「至多一条建议」：镜头前的人在说话的间隙扫一眼，**能处理的信息量是 1 条，不是 3 条**。给多了等于没给。

为什么字幕区要「独立底色容器」：把当前字幕块和上面的阶段/建议做视觉分隔，主播一眼就能扫到「现在在播这句话」。历史 1–3 行保持渐隐，更能突出当前句。

为什么位置锁死：直播中每次找信息都要重新扫视，位置固定才能形成肌肉记忆。

## 9. 执行顺序与验收锚点

对应 PRD §9 交付切片：

| 切片 | 本设计文档的相关约束 | 完成判据 |
|------|---------------------|---------|
| R1 | §5 顺序刚性；token 表是唯一来源 | 全站无硬编码色值；grep 验证 |
| R2 | §6 三 dock 职责边界；§4 规矩一、二 | 每 dock 有标题栏 + 可折叠；状态不再三处冗余 |
| R3 | §7 五要素位置锁死；零控件 | Stage 上无任何可操作控件；字幕区有独立底色容器 |
| R4 | §4 规矩三分流 | banner 仅剩常驻阻断；一次性事件走 toast |
| R5 | §6.3 工作区平级 | 回看有独立入口，非模式切换 |
| R6 | 全部 | 视觉验收 + 功能闭合 + 沿用验收 |

> **G4 口径**：Stage 通道只读边界代码已随 PR #22 合入 main，本版不重做实现，只随 R6 做验收复验。

**视觉验收的简单自检**（R1–R5 每片合入前问一遍）：

1. 这个界面里，层级是靠描边 / 标题栏，还是靠亮色块？
2. 同一个状态，在这屏里出现了几次？
3. 这条提示，用户需要「处理」还是只需「知道」？载体对不对？
4. 新写的 CSS 里，有没有出现新的十六进制色值？

四问全过，就算符合本设计思路。

## 11. 待定项（依赖 PRD §10 开放问题）

以下判断尚未收敛，实现前需拍板：

1. **Stage 强光模式**（PRD 开放问题 1）：若做，是同 token 表的第二档对比度，还是独立 token 集？倾向后者，避免一表两义。
2. **全局快捷键**（开放问题 3）：若进 v1.0.0，需明确「盲操」场景下的键位，且状态栏要能显示按键提示。
3. **品备注多品结构**（开放问题 4）：若改为一品一行，右 dock 需要新增列表型组件，超出本文 §6 的单框假设。
4. **dock 折叠记忆的粒度**：按工作区分别记忆，还是全局一套？倾向按工作区，因为盯播与回看的右 dock 内容不同。
5. **推流 / 发券提醒控件缺 FR 规格**：PRD 头部 A5 与 §3.3 已裁定本版要画该控件（出站仍后置、触发依赖未合的 PR #23），但 §6 功能需求里还没有对应 FR 条目（FR-01–FR-19 均未覆盖）。参考图已按「右 dock 内两条提醒行」画出，实现前需要 PRD 补一条 FR，明确：控件形态（提醒行 / 按钮？）、触发条件与不可用态、无触发时的空态、是否可手动确认。**在补上 FR 之前，参考图里这一块只是占位示意，不算已定规格。**
