## 1. 一句话定位

**本人自用起步、面向抖音直播间小团队的桌面 AI 盯播教练。**

已交付的主路径不变：听本机正在播的直播声，实时转写，按滑动窗口对照本地话术框架，标出语速 / 节奏 / 内容问题，在应用内提示「讲偏了什么」。

v0.3.0 的方向是：同一套引擎长出**两套界面**（主播 / 助播抬头大屏，中控详细盯播台），并在抖音直播场景里预留**推流信号、发券信号**；舆情触雷时的**播出侧闭麦**只作为后续可选能力，默认关闭。它赋能的是讲解有没有按框架落地，不是 GMV 总控。

## 2. 背景与问题

直播中人很难同时「讲好」又「对照框架自查」。事后复盘太晚；企业合规巡检太重；提词器只负责滚稿，不负责判问题。

公开市场上几乎没有同时满足：**桌面环回 + 可切换流式 ASR + 可配置滑动窗口 + 对照本地话术框架做语速/节奏/内容督导** 的成品（详见 `docs/research/competitors.md`）。

直播在营销漏斗里主要踩「停留 → 互动 → 点击 → 加购」这一截：讲解和节奏是否按预定框架执行。投流、改价、挂链、履约都不是本产品的活。主播在镜头前只能吃短信号；助播适合抬头看；中控适合看可解释的问题时间轴；复盘要的是场次证据，不是再做一块成交大屏。

## 3. 目标用户、平台与场景

### 3.1 角色

| 角色 | 直播中看什么 | 要什么 |
|------|--------------|--------|
| 主播 | 与助播同一块抬头大屏 | 不打断讲解的短信号：阶段、角标、一句建议 |
| 助播 | 抬头大屏 | 知道何时口头补哪一句，而不靠吼 |
| 中控 | 详细盯播台 | 问题时间轴、转写片段、框架命中；可并排本场品备注 |
| 播后复盘 | 停播后的详细台只读 / JSONL | 这场有没有按框架讲，而不是一篇感觉 |

场控、投放、客服不单独立项。腰部以上若有场控，先看中控这套详细台，不为此再做一套巡检系统。

**非目标用户（仍有效）**：需要多直播间巡检、拉流固证、公网多租户的企业监管方。

### 3.2 平台硬约束

本版**只做抖音直播**。不做快手、淘宝直播、视频号，也不做多平台抽象层。

分析音源仍是**本机系统环回**（主播电脑正在播出的声音）。产品不绑定某一个直播间，也不去打开或抓取直播间页面。

### 3.3 场景样例：韩束抖音直播间

用户故事和验收场景用公开直播间作举例：

- 名称：**韩束抖音直播间**
- 公开地址：<https://live.douyin.com/295178185857>
- 房间号示意：**295178185857**（直播间地址会变，产品不绑定该房间）

文档**不编造**该直播间未公开的 GMV、订单、在售 SKU、真实口播或话术。框架例句是虚构的美妆护肤带货口径，只为把验收说清楚，见 §10。

### 3.4 用户故事（方向验收，当前版本不做门禁）

**US-1 助播抬头（M5，未实现）**

作为韩束抖音直播间的助播，我在镜头侧看抬头大屏，以便知道现在该补哪一句，而不抢主播的注意力。主播看同一块屏，不另做第三套界面。

- 音源是本机环回，不是去拉 `https://live.douyin.com/295178185857` 的流。
- 大屏主视觉只有三件事：当前阶段、未读角标、一句建议。例句（虚构框架）：阶段「讲品」，建议「补：点名核心成分与适用肤质」。
- 问题时间轴、转写长文、成交数字不放在这块主视觉上。
- 建议来自已有规则引擎，不另跑一套点评模型。

**US-2 中控盯播（M5，未实现）**

作为韩束抖音直播间的中控，我在详细盯播台按时间轴看问题，点开能看到转写片段和命中的框架条目，以便区分漏讲和触雷。

- 每条问题仍要能对应：时间窗 + 转写片段 + 框架条目。
- 台面可以留「本场品」并排位。第一期只接受手填备注或本地框架标题，可以空着。
- 界面上固定写明：这里不是 GMV / 订单 / 投流总控，不展示、也不拉取该直播间未公开的成交数据。
- M6 的推流信号、发券信号出现在这块台子上，不占用大屏主视觉。

**US-3 播后复盘（M4 P1 是底座，M5 复用中控台，均未完成）**

作为韩束抖音直播间的复盘角色，停播后我回看本场问题时间轴和必讲覆盖，确认讲解有没有按框架落地。

- 数据来自本机 `sessions/<sessionId>/session.jsonl`，不上传。
- 复盘结论是框架覆盖和问题记录，不是该房间的 GMV 或 SKU 战报。
- M4 P1 的最简回看 UI 还没做。在那之前，复盘只有落盘文件，没有应用内回看。

## 4. 核心 Job

> 直播进行中，用近窗文稿对照预定框架，**及时发现并呈现「讲偏了什么」**。

v0.3.0 演进（未实现，不改变上面这句已交付的 Job）：

1. 同一条结论用两种带宽呈现：大屏一句可执行建议，详细台可解释。
2. 条件满足时，可以向中控 / 本地 OBS / 官方中控工具发**信号**（建议推流、建议发券）。软件不代替中控改价挂链。
3. 不该聊的话题，现在仍是应用内触雷提醒。立刻闭麦是后续可选，默认关。

不是：开播提醒、比价、GMV 中控、纯违禁词审核、提词滚屏、快手 / 淘宝 / 视频号、未授权抓取抖音私有接口。

## 5. 需求优先级

> 实现状态（2026-10-18）：**Must 与既有 Should 的主路径已交付**（M1–M3）。流式 ASR 可切换实现：默认本地 **FunASR sidecar**，**讯飞 RTASR 标准版**为第二 ASR。第 5.2 节第 4 条（讯飞凭据门禁）与第 3 条的设置页密钥收敛已落地。第 5、6 条（JSONL 回看、健康预检）仍属 M4 P1，代码未做。第 5.3、5.4 节全部是方向，未实现。

### 5.1 Must（没有就不是这个产品；已交付）

1. 本机**系统声卡环回**采音，持续把音频帧送给 ASR。这里的「送给 ASR」不是直播间推流；直播推流见 §7
2. **流式 ASR 适配层**（可切换实现；直播中不热切换）。默认 **FunASR**，讯飞为第二实现
3. **滑动窗口分析**：默认每 **1 分钟**分析过去 **5 分钟**（均可配置）
4. 对照本地**话术框架文件**，产出三类问题：**语速 / 节奏 / 内容**
5. **应用内**问题列表 + 角标；每条问题可解释（时间窗 + 转写片段 + 触达的框架条目）

舆情把控的 Must 仍是第 5 条里的应用内提醒（`avoid` 触雷）。闭麦不是 Must。

### 5.2 Should · 近期工程（M4）

既有第 1–3 条主路径已交付。第 4–6 条为 v0.2.0 写入，归 M4。v0.3.0 不把它们挪走。

1. 问题附带一句建议动作（放慢 / 补卖点 X / 回到促单段）。**已交付**
2. 讲点覆盖勾选（`must_say` 已讲 / 未讲），与问题列表并存。**已交付**
3. 基础设置页：窗口时长、分析间隔。云端凭据只走讯飞（APPID + APIKey），经本机安全存储，不进前端明文。**通用「云 ASR 密钥」废弃**：没有适配器消费；设置页已隐藏填写入口，只保留清除旧密文。有效路径仅讯飞凭据。**已落地**
4. **云 ASR（讯飞）启用前须凭据就绪，否则不可开始**（未配置 APPID/APIKey 时开始按钮不可用，准备区写明「未配置讯飞 APPID/APIKey，请到设置页填写」）。**已落地**
5. 停止后**本场 JSONL 可回看**（最简 UI：本场问题 / 字幕摘要即可，不要求导出文件）。**M4 P1，未做**
6. （可选）开始前 **ASR 健康预检**展示在准备区（FunASR / 讯飞）；失败时不可开始。**M4 P1，未做**

### 5.3 Should · 产品方向（M5 双端，未实现）

同一软件、同一会话、两套界面。音源仍是本机环回。详见 §6。

1. **抬头大屏**（主播 / 助播）：当前阶段、未读角标、一句建议
2. **中控详细盯播台**：问题时间轴、转写片段、框架命中；预留本场品备注并排位，并标明不是 GMV 总控
3. 两套界面读同一套规则结果，不各算各的

### 5.4 Could · 分阶段联动（M6 / M7，未实现）

归 M6，见 §7：

1. 盯播过程中发出**推流信号**（中控台始终可见；发给本机 OBS 或 webhook 前须人工确认）
2. 条件满足时发出**发券信号**（给中控工具；默认经人工确认后才出站）
3. 软件自己调用抖音接口完成推流或发券：更后，且只在官方能力与授权说清楚之后。不进 M6 退出标准

归 M7，见 §8：

4. 舆情 / `avoid` 词库命中时的**可选闭麦**。默认关。Must 路径仍是应用内提醒
5. 无人工确认的自动闭麦不进入 M7 的默认路径

更远、本路线图不排期：系统通知、直播流 URL 拉流、开播监测、应用内框架编辑器、语调 / 情感声学分析、完整场后报告导出、多直播间、公网多用户、与「直播比价」数据打通、自动阶段识别模型。

### 5.5 明确不做（本版）

- 快手、淘宝直播、视频号及其他平台
- 开播监测、按 URL 拉流（包括不拉取韩束直播间页面，不把该 URL 当音源）
- 未授权抓取抖音私有接口，或抓取未公开的 GMV、订单、话术
- 比价；把盯播做成 GMV / 投流总控
- 系统通知、公网多用户、企业断流 / 固证
- 无框架的「AI 自由点评」占满主路径
- 默认开启的播出侧闭麦

v0.2.0 把播出侧 mute 写在 MVP「明确不做」里。v0.3.0 **不把它提前做成 Must**：M7 之前行为与现在相同，只提醒、不闭麦。闭麦留在可选高风险能力，默认关。

LiveNotes 不升格为正式能力，见 §5.6。

### 5.6 实验（不进正式 Should）

**LiveNotes 侧栏记事**已在界面出现，本版仍标为实验：渲染进程本地记事，不进规则引擎，也不进复盘。可折叠或日后移除，不作为验收项。

## 6. 双端展示（M5，未实现）

同一套盯播引擎（环回 → ASR → 滑动窗口 → 规则）投影成两个表面。禁止第二套规则。

```
                    ┌─────────────────────┐
                    │  同一套盯播引擎      │
                    │  环回→ASR→窗口→规则 │
                    └─────────┬───────────┘
               ┌──────────────┴──────────────┐
               ▼                             ▼
     【端 A · 抬头大屏】              【端 B · 中控详细盯播台】
     主播 / 助播                     中控；停播后复盘复用此端
     · 阶段                          · 问题时间轴
     · 未读角标                      · 转写片段 + 框架命中
     · 一句建议                      · 本场品备注（可空）
     · 少字、大字                    · 固定说明：不是 GMV 总控
```

| 项 | 口径 |
|----|------|
| 形态 | 同一个桌面应用里的两个窗口，不是两套安装包，也不是公网多租户 |
| 机器 | M5 锁**同一台电脑**。另一台机器看中控是开放问题，不进 M5 |
| 阶段 | 中控在详细台点选当前阶段（默认框架 `stages` 的第一项；没有 stages 就显示「直播中」）。大屏只读跟随。自动识别阶段不进 M5 |
| 一句建议 | 取当前未读问题里优先级最高的那条 `suggestion`。没有未读问题时，大屏不编一句 |
| 品 / 其他数据 | 并排位可以预留。第一期内容只是手填的本场排品备注，或本地框架标题。成交、投流、订单不接入 |
| 边界文案 | 详细台可见固定句：「内容盯播，不是 GMV 总控。」 |

## 7. 推流信号与发券联动（M6，未实现）

盯播**已经在进行**（本机环回已在听）时，规则命中可以向外表示「建议推流」或「建议发券」。这是出站信号，不是采音，也不是发现开播。

| 能力 | 数据方向 | 本版 |
|------|----------|------|
| 开播监测 | 发现某个房间开播了 | **不做** |
| URL 拉流 | 把 `live.douyin.com/...` 的音视频拉进来当分析音源 | **不做**。韩束链接只是场景名字 |
| 音频送给 ASR | 环回 PCM → ASR | **已交付**（§5.1）。不要把它叫成直播推流 |
| 推流信号 | 告诉中控 / OBS / 官方工具：建议开始或切换推流 | **M6，未实现** |
| 自动推流 | 本软件直接调用平台接口完成推流 | **开放问题**。需官方能力与商家授权，不进 M6 |
| 发券信号 | 告诉中控工具：条件已满足，可以发券 | **M6，未实现**。默认人工确认后才出站 |
| 自动发券 | 本软件直接调用平台发券 | **开放问题**。同上，不进 M6 |

M6 退出时只做这三档出站，且前两档以外不出网：

1. **只在中控台显示信号**（始终有）
2. 人工确认后，发给**本机 OBS**（本地 WebSocket 一类接口）
3. 人工确认后，发给**可配置 webhook**（地址和密钥在本机安全存储，不进前端明文）

不接入未授权的抖音私有接口。不在盯播里保存券面额、券库存或推流地址作为真相源；那些留在官方中控或 OBS。

触发条件用本地规则配置，例句来自 §10 的虚构框架，不是韩束真实场控口令：

- 推流信号例：中控已把阶段点到「促单」，且本场已覆盖「讲清今日机制与到手价口径」
- 发券信号例：当前阶段为「促单」，该 `must_say` 已覆盖，且当前窗没有 `avoid` 命中

未确认前，信号停在中控台。同一规则在冷却期内不重复刷信号。

## 8. 舆情把控与可选闭麦（M7，未实现）

检测到不该聊的话题时：

| 动作 | 优先级 | 状态 |
|------|--------|------|
| 应用内 critical 提醒（时间窗 + 片段 + 框架条目） | **Must，已交付**（`avoid` 触雷） | 现在就会这样 |
| 中控台弹出「确认闭麦」 | M7，开关默认关 | 未实现 |
| 确认后让本地 OBS / 调音路径静音 | M7，依赖上一行的人工确认 | 未实现 |
| 不经确认立刻自动闭麦 | 不在 M7 默认路径 | 未实现；是否以后做，见开放问题 |

闭麦是播出侧干预，误杀会让直播突然无声。风险包括：ASR 错字、谐音、正常否定句（例如口播「我们不说根治」仍命中「根治」）。

开关口径：

- 默认**关**。关着的时候行为与今天相同，只提醒
- 话术框架 JSON **不能**把闭麦打开。只有应用设置里的显式开关可以
- 开关打开后，默认仍是人工确认，不是立刻闭麦
- 设置页写明误杀风险。关闭开关立即停止后续闭麦信号
- 闭麦不用来回避平台自身的记录或审核，本产品也不提供这类能力

词库第一期复用框架 `avoid[]`。单独的「舆情词库文件」可以后加，不阻塞 M7 的开关设计。社区里 OBS 脏话过滤一类「词库 + 延时静音」只作思路参考，不是已集成的插件。

## 9. 播效对比：三类问题的 v0 定义

| 维度 | MVP 判定（规则引擎优先） | 说明 |
|------|--------------------------|------|
| **内容** | `must_say` 近窗未覆盖 → 漏讲；命中 `avoid` → 触雷；可选简单关键词/相似度跑题 | **最重要**。触雷的播出侧闭麦见 §8，不改变本行 |
| **语速** | 近窗有效字数 / 有效时长 → 字/分钟，对照 `pace.min`～`pace.max` | 可参考客服质检惯例 |
| **节奏** | 近窗静音占比、句密度、超长停顿或连珠炮 | 粗规则即可 |
| **语调** | **不进 MVP**；路线图标为 v2（声学/情感标签） | 避免虚指标 |

## 10. 话术框架（文件优先）

## 11. 产品主流程

已交付路径：

1. 打开桌面应用 → 加载话术框架文件
2. 选择环回设备 → 开始盯播
3. 实时字幕滚动（转写缓冲）
4. 每到分析间隔：取近窗文稿 → 跑规则 → 写入问题列表 / 更新角标与讲点覆盖
5. 停止盯播 → 本场问题仍可浏览。JSONL 已落盘（`sessions/<sessionId>/session.jsonl`）。最简回看 UI 见 §5.2 第 5 条，归 M4 P1，未做

方向路径（未实现，不替换上面 5 步）：

6. M5：同一会话同时打开大屏与中控台。中控点选阶段，大屏只显示阶段 / 角标 / 一句建议
7. M6：规则命中后，中控台出现推流信号或发券信号；人确认后才发给本机 OBS 或 webhook
8. M7：仅当闭麦开关打开且人确认后，才发静音信号。默认不发生

## 13. 验收标准

### 13.1 当前产品（M1–M3 + M4 P0，继续有效）

1. 开盯后连续 ≥30 分钟不断采、不断字。**30 分钟真环回仍为人工验收**（仓库内只有 Fake 音频时钟单测，不算闭环）
2. 每条问题能对应：时间窗 + 转写片段 + 框架条目
3. 人工抽检：抽 10 个问题窗，≥7 条认为「确实该改」。仓库内尚无抽检记录，清单归 M4 P1
4. 分析触发后，约 1～2 分钟内列表可见新问题。**漏讲要连续两个完整分析窗口才报，首条漏讲可能 >2 分钟**（默认 5 分钟窗时更久）。这是降误报的口径，不用「1～2 分钟」去卡漏讲首条
5. 无明显问题时不强行刷屏；角标 = 未读问题数

### 13.2 方向验收（M5–M7 的退出条件，不是本迭代门禁）

见 §14 各里程碑的退出标准，以及 §3.4 的三条韩束用户故事。在对应里程碑开始编码之前，这些条款不拿来判定当前版本失败。

## 15. 合规、安全与项目边界

- 密钥不进前端明文，不进仓库。讯飞凭据已走 Electron `safeStorage`。以后若接抖音开放平台，Key 同样只在主进程 / 本机 `safeStorage`
- webhook 地址和令牌按密钥处理：主进程持有，日志脱敏，渲染进程只知道「已配置 / 未配置」
- **不鼓励、不设计**未授权抓取抖音私有接口、房间成交或未公开话术。韩束直播间 URL 只出现在场景说明里，客户端不请求它
- 推流与发券优先做成**信号**，交给中控、本地 OBS 或官方中控工具。直接调平台 API 标为开放问题：需要官方能力与商家授权，未关闭前不实现
- 闭麦默认关，并保留人工确认。误杀导致无声的风险写进设置，不把「立刻切断」写成默认体验
- 框架里的功效承诺会被工具督促去讲。`avoid` 用来挡住绝对化疗效和医疗化表述；工具不背书违法宣传
- 与「直播比价」：盯播不做价格和评价对比；两边数据打通不在本版

## 16. 开放问题

### 16.1 v0.2.0 已结案（保留，不再打开）

1. **默认 ASR**：本地 **FunASR sidecar**。云端第二实现是 **讯飞 RTASR 标准版**。直播中不热切换。见 SDD ADR-005 / §2.1。
2. **节奏阈值**：以 SDD §9.3 与代码里的 `RHYTHM_DEFAULTS` 为准，PRD 不另写一套数字。
3. **结束后落盘**：已写本地 JSONL（`sessions/<sessionId>/session.jsonl`）。应用内最简回看仍是 M4 P1，不是开放问题。

### 16.2 v0.3.0 新开（评审用，未关闭前不实现对应出站）

1. **大屏信息量**：是否锁死「阶段 + 角标 + 一句建议」？助播要不要在三件套之外再看一条高优问题标题？
2. **中控并排的「品」**：第一期是否只允许手填备注？如果允许粘贴外部指标，怎样保证它不会滑成伪 GMV 面板？
3. **双端是否永远同机**：另一台电脑看中控要不要做？若做，会话怎么同步，还算不算 M5？
4. **推流信号的第一接收端**：仅中控文案、本机 OBS，还是通用 webhook？自动调用抖音推流 API 是否明确永不由本产品发起？
5. **发券**：触发条件放框架还是中控本地规则？出站是否永远必须人工确认？券种、库存、面额是否规定永不进入盯播？
6. **官方能力**：抖音开放平台是否提供可授权的推流 / 发券接口，商家授权边界在哪？未确认前，私有接口保持禁止。
7. **闭麦误杀**：M7 是否只做到「确认后发 OBS 静音信号」？无确认自动闭麦要不要永久排除？默认关的开关能否被框架或远程配置覆盖（建议不能）？
8. **复盘北极星**：框架覆盖率、高优问题密度，还是沿用「10 窗里 ≥7 条确实该改」的人工抽检？指标用来证明讲解执行，不用来承诺 GMV。
